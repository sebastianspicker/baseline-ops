# Phase 1.2 Security Audit Findings

Deep security audit of all operational scripts and library modules.
Excludes previously fixed items S1-S5 from iterations 1-5.

## Findings

| ID | Severity | File | Line | Category | Description | Recommended Fix |
|----|----------|------|------|----------|-------------|-----------------|
| S6 | Medium | `scripts/33-AdvancedAuditPolicy-Audit.ps1` | 365 | Command injection | `$subName` from JSON config is interpolated into `auditpol.exe` `/subcategory:` argument without validation. A crafted subcategory name like `"Logon" /success:enable /set /subcategory:"Object Access"` could inject extra arguments. The value flows from user-provided JSON (`$desired` object parsed from `-DesiredPolicyJson`), through `$subProp.Name`, into `$auditArgs = @('/set', "/subcategory:$subName", ...)`. While `Invoke-Auditpol` uses array splatting (limiting shell injection), `auditpol.exe` itself parses the combined `/subcategory:VALUE` token and could interpret embedded spaces/slashes. | Validate `$subName` matches `^[a-zA-Z0-9 /\-]+$` (no quotes, no `/` except in known subcategory names) before passing it to `Invoke-Auditpol`. Alternatively, use the GUID-based `/subcategory:{GUID}` syntax which is injection-proof. |
| S7 | Medium | `scripts/21-EmergencyKillSwitch.ps1` | 477 | Unsafe registry path | `$Run.Effective.RegKey` is loaded from JSON config (`Get-ConfigValue -Config $config -Name 'RegKey'`) and passed directly to `New-Item -Path $RegKey` and `Set-ItemProperty -Path $RegKey` at line 283 without any validation. A crafted JSON config could point this to any arbitrary registry key (e.g., `HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion\Run`), allowing the script to create/overwrite values in security-sensitive locations. | Validate that `$RegKey` starts with a known safe prefix (e.g., `HKLM:\SOFTWARE\KillSwitch\`) using a regex allowlist before using it. Reject keys outside the expected namespace. |
| S8 | Medium | `scripts/21-EmergencyKillSwitch.ps1` | 478,502-504 | Input validation gap | `$Run.Effective.RulePrefix` is loaded from JSON config without validation and used to construct firewall rule names (`$RuleInName`, `$RuleOutName`, `$RuleBgName`) and `DisplayName` parameters for `New-NetFirewallRule`. While firewall rule names have length limits, a malicious value could create confusingly-named rules (e.g., mimicking system rules) or contain special characters that cause parsing issues. | Validate `$RulePrefix` against `^[a-zA-Z0-9\-_]+$` and enforce a reasonable max length (e.g., 64 chars). |
| S9 | Medium | `scripts/16-Sysmon-Config-Updater.ps1` | 391,394,400 | Command injection (wevtutil) | `$name` variable (hardcoded to `'Microsoft-Windows-Sysmon/Operational'`) is passed to `wevtutil` via double-quoted string interpolation: `wevtutil gl "$name"` and `wevtutil sl "$name" /e:true`. While currently hardcoded and safe, this pattern is fragile. If the channel name were ever made configurable, the double-quoted interpolation allows a value containing `" /q:` to inject additional wevtutil arguments. The same pattern appears in script 17 at lines 437 and 475. | Use array-based invocation via `Invoke-Wevtutil` wrapper instead of direct `wevtutil` calls with string interpolation. Replace `wevtutil gl "$name"` with `Invoke-Wevtutil -Arguments @('gl', $name) -CaptureOutput`. |
| S10 | Medium | `scripts/36-Backup-Readiness-Audit.ps1` | 179 | WQL injection | `$driveId` derived from `$env:SystemDrive` is interpolated into a CIM filter: `Get-CimInstance -ClassName Win32_LogicalDisk -Filter ("DeviceID='{0}'" -f $driveId)`. While `$env:SystemDrive` is typically `C:`, on a compromised host the environment variable could be manipulated to contain a single quote, altering the WQL filter semantics. | Escape single quotes: `$escapedDriveId = $driveId -replace "'", "''"` before interpolation into the filter string. |
| S11 | Low | `scripts/45-WEF-Client-Forwarding-Readiness-Audit.ps1` | 157 | WQL injection (hardcoded) | `Get-CimInstance -ClassName Win32_Service -Filter "Name='WinRM'"` uses a hardcoded string literal `WinRM`, so this is not currently exploitable. However, this CIM filter pattern does not follow the project convention of escaping single quotes before interpolation, creating a maintenance risk if the name is ever refactored to a variable. | No immediate fix needed, but add a comment noting the value is hardcoded and safe. If refactored to a variable, apply the `$name -replace "'", "''"` pattern. |
| S12 | Medium | `scripts/25-WinGet-Config-Baseline-Runner.ps1` | 408-414,438 | Argument injection via ExtraArgs | `$ExtraArgs` (aliased as `Args`) accepts arbitrary string arrays from the user or JSON config and are appended directly to the `winget.exe` argument list at line 438: `$argsCommon += $ExtraArgsEffective`. A crafted JSON sidecar file could inject arguments like `--force` or `--accept-source-agreements` that bypass intended safety controls (e.g., the script's own `AcceptAgreements` flag). More concerning, WinGet arguments could include `--override` which passes arbitrary arguments to the installer. | Validate `$ExtraArgsEffective` entries against a denylist of dangerous WinGet flags (e.g., `--override`, `--force`, `--ignore-security-hash`). At minimum, reject entries starting with `--override`. |
| S13 | Low | `scripts/09-SupportBundle.ps1` | 543-547 | Command argument construction | In `SB_ExportEventLogEvtx`, the XPath query is constructed and embedded in a format string: `$qArg = '/q:"{0}"' -f $xpath`. The resulting `$qArg` is then passed as a single token to `& $wevt epl $LogName $OutFile $qArg /ow:true`. The `$LogName` variable comes from a hardcoded array at line 870, so it is safe today. However, the `$qArg` construction with embedded quotes is fragile -- if `$xpath` ever included user data, the quoting could be broken. | Refactor to use `Invoke-Wevtutil` wrapper with proper array-based arguments instead of direct `& $wevt` invocation with manual quoting. |
| S14 | Low | `scripts/12-Suspicious-Artifact-Grabber.ps1` | 653 | Path injection in Export-ScheduledTask | `Export-ScheduledTask -TaskName $t.TaskName -TaskPath $t.TaskPath` passes task names from `Get-ScheduledTask` output directly to `Export-ScheduledTask`. While these come from the OS rather than user input, the output file path at line 654 is constructed using a basic sanitization (`-replace '[\\/:*?"<>|]','_'`). A task with a name containing `..` sequences after sanitization could potentially write outside the intended directory. | Apply `Assert-NoPathTraversal` or `Test-PathUnderRoot` on the constructed `$xmlPath` before writing. |
| S15 | Low | `lib/Evidence.psm1` | 52 | Path traversal (incomplete regex) | `Copy-ToEvidence` checks for `..` in paths using `-match '\.\.'`, which correctly blocks literal `..` sequences. However, this check operates on the raw string before environment variable expansion. A path like `%TEMP%\..\..\..\Windows` would not contain `..` if `$SourcePath` is the unexpanded form but the actual traversal happens during file operations. In practice, `Test-Path -LiteralPath $SourcePath` at line 56 would expand the path, but the `..` check at line 52 operates on the original string. | Expand environment variables in `$SourcePath` before the traversal check, or use `[System.IO.Path]::GetFullPath()` and then verify the resolved path is under an expected root using `Test-PathUnderRoot`. |
| S16 | Low | `lib/External.psm1` | 349 | Missing input validation on New-ScheduledTask | The `New-ScheduledTask` wrapper accepts `$TaskName` and `$TaskRun` without any validation. While it correctly uses array-based argument passing to `schtasks.exe` (preventing shell injection), there is no validation that `$TaskName` is safe (e.g., no path traversal in task folders) or that `$TaskRun` does not contain dangerous payloads. Any caller must perform their own validation. | Add a `[ValidatePattern]` attribute or inline validation on `$TaskName` (e.g., `^[a-zA-Z0-9\-_\\]+$`) matching the convention established in S3. Document that callers are responsible for `$TaskRun` validation. |
| S17 | Low | `scripts/17-Sysmon-Rule-Drift-Sensor.ps1` | 546 | Unconstrained script execution | `Start-Process -FilePath "powershell.exe" -ArgumentList $argList` where `$argList` includes `-File $ScriptPath` and the `$ScriptPath` comes from the function parameter. While the calling code at line 537 uses `$ScriptPath` which appears to be an internally-derived path (the script remediation helper), there is no validation that the path is under an expected directory or that the file is a `.ps1` script. | Validate `$ScriptPath` using `Test-PathUnderRoot` and `Test-SafeScriptName` before execution. |
| S18 | Info | `scripts/09-SupportBundle.ps1` | 854-862 | Config-driven file copy without path validation | `$proofCandidates` paths come from the JSON config (`$Config.ProofOutFiles.*`) and are passed to `SB_CopyIfExists` which copies them into the bundle. These paths are not sanitized with `Sanitize-Path` or checked for path traversal. While `Copy-Item -LiteralPath` limits the risk, a crafted config could cause sensitive files outside the intended proof directory to be included in the ZIP bundle. | Apply `Sanitize-Path` to each proof candidate path before passing to `SB_CopyIfExists`. |
| S19 | Info | `scripts/09-SupportBundle.ps1` | 831-832 | Config-driven output directory | `$ProofDir` is loaded from JSON config (`$Config.Paths.ProofDir`) without path validation. The entire support bundle (including ZIP file) is created under this directory. A crafted config could redirect the bundle to a sensitive location. | Apply `Sanitize-Path` or at minimum `Assert-NoPathTraversal` on the `$ProofDir` value. |
| S20 | Info | `scripts/12-Suspicious-Artifact-Grabber.ps1` | 937-941 | Config-driven output directory | `$base` from `$cat.OutputBase` controls where the entire IR grabber output (including collected artifacts and ZIP) is written. No path sanitization is applied. A crafted catalog JSON could redirect output to a sensitive directory. | Apply `Sanitize-Path` to `$cat.OutputBase` before using it as the output root. |

## Summary

### By Severity
- **Medium**: 5 findings (S6, S7, S8, S9, S10, S12)
- **Low**: 5 findings (S11, S13, S14, S15, S16, S17)
- **Info**: 3 findings (S18, S19, S20)

### By Category
- **Command/argument injection**: S6, S9, S12, S13
- **WQL/CIM injection**: S10, S11
- **Unsafe registry operations**: S7
- **Input validation gaps**: S8, S16
- **Path traversal / unsafe paths**: S14, S15, S18, S19, S20
- **Unconstrained execution**: S17

### Key Observations

1. **No critical findings.** The most impactful issues from earlier iterations (WQL injection, PS heredoc code injection, unquoted schtasks) have been addressed. The remaining findings are defense-in-depth improvements.

2. **Config-driven paths are the main theme.** Several scripts accept directory paths from JSON config files without sanitization. While these configs are typically deployed by admins, a compromised or malicious config could redirect output or create files in unintended locations.

3. **The `Invoke-NativeCommand` / `Invoke-Wevtutil` pattern is well-designed** but underused. Scripts 16 and 17 still call `wevtutil` directly with string interpolation instead of using the safe wrapper from `lib/External.psm1`.

4. **The `Copy-ToEvidence` traversal check is functional but could be bypassed** by unexpanded environment variables. This is a minor theoretical concern since the function also uses `Test-Path -LiteralPath` which handles expansion.

5. **The 00-Run-Local.ps1 script has excellent security controls** -- symlink detection, path-under-root validation, optional hash verification, and signature checking. This is a good model for other scripts.
